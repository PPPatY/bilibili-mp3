# Bilibili MP3 批量下载功能设计文档

**日期**: 2026-09-18  
**版本**: 1.0  
**状态**: 待实现

## 目标

为现有的 Bilibili MP3 本地转换工具增加自动批量下载功能，支持从用户指定的合集视频链接自动获取后续所有视频，并按顺序批量转换为 MP3。

## 核心需求

1. **合集解析**：用户提供一个 Bilibili 视频链接，系统自动识别所属合集并获取完整视频列表
2. **灵活起点**：支持从指定集数开始下载（手动指定起点）
3. **断点续传**：记录已下载进度，重启后自动跳过已完成的视频
4. **智能去重**：检查本地已存在的 MP3 文件，自动跳过
5. **串行下载**：一次只下载一个视频（并发数=1），避免带宽占用和触发限流
6. **容错机制**：单个视频失败后自动重试3次，超时后跳过并继续下一个
7. **下载间隔**：每个视频下载完成后等待15秒再开始下一个
8. **独立管理界面**：提供完整的批量任务管理页面，可后台运行

## 用户场景

### 场景1：首次批量下载
1. 用户打开批量管理页面（batch.html）
2. 粘贴合集中任意一集的链接（如：https://www.bilibili.com/video/BV1xx）
3. 系统解析出合集信息：《未来有悔》系列，共50集
4. 用户选择从第1集开始，选择码率192k
5. 点击"开始批量下载"
6. 系统自动逐个下载第1-50集，每集间隔15秒
7. 界面实时显示进度：第7集/共50集 (14%)

### 场景2：断点续传
1. 上次下载到第8集时用户关闭了浏览器
2. 用户重新打开批量管理页面
3. 系统自动检测到未完成的任务
4. 提示："检测到未完成任务《未来有悔》系列，已完成7集，是否继续？"
5. 用户点击"继续"
6. 系统从第9集开始继续下载

### 场景3：手动指定起点
1. 用户已经手动下载了前10集
2. 现在想批量下载剩余的第11-50集
3. 粘贴第11集的链接
4. 系统识别合集，默认从第11集开始
5. 开始批量下载

## 数据模型

### 批量任务对象 (BatchJob)

```javascript
{
  batchId: "uuid",                    // 任务唯一标识
  collectionTitle: "合集名称",         // 合集标题
  collectionUrl: "https://...",       // 合集页面URL
  videos: [                           // 视频列表
    {
      bvid: "BV1xx411c7mD",           // BV号
      title: "第1集 标题",             // 视频标题
      episode: 1,                     // 集数
      url: "https://...",             // 视频页面URL
      status: "completed",            // pending/processing/completed/failed/skipped
      jobId: "server-job-uuid",       // 服务端转换任务ID
      retries: 0,                     // 已重试次数
      error: null,                    // 错误信息
      filename: "第1集.mp3",          // 输出文件名
      completedAt: 1726646400000      // 完成时间戳
    }
  ],
  startIndex: 0,                      // 起始索引（从第几个视频开始）
  currentIndex: 7,                    // 当前处理索引
  status: "running",                  // pending/running/paused/completed/cancelled/failed
  createdAt: 1726646400000,          // 创建时间
  updatedAt: 1726646400000,          // 最后更新时间
  settings: {
    bitrate: "192k",                  // 音频码率
    retryLimit: 3,                    // 最大重试次数
    interval: 15000                   // 下载间隔（毫秒）
  },
  stats: {
    total: 50,                        // 总视频数
    completed: 6,                     // 已完成数
    failed: 1,                        // 失败数
    skipped: 0,                       // 跳过数
    pending: 43                       // 待处理数
  }
}
```

## 工作流程

### 1. 合集解析流程

```
用户输入视频链接
    ↓
batch.js 发送消息到 content.js
    ↓
content.js 在当前标签页执行
    ↓
方案A：从页面DOM解析合集信息
  - 读取播放器组件的合集列表
  - 提取每集的 BV号、标题、集数
    ↓
方案B：通过 Bilibili API 获取
  - 解析视频所属合集ID
  - 调用公开API获取合集视频列表
    ↓
返回合集信息到 batch.js
    ↓
batch.js 渲染视频列表供用户确认
```

**选择方案A（DOM解析）**：
- 优点：不依赖API稳定性，使用浏览器已有的登录态
- 缺点：页面结构变化可能导致解析失败
- 实现：通过 `document.querySelector` 提取合集组件数据

### 2. 批量下载流程

```
用户点击"开始批量下载"
    ↓
batch.js 创建 BatchJob 对象
    ↓
发送消息到 background.js
    ↓
background.js 启动批量任务调度器
    ↓
┌─────────────────循环────────────────┐
│ 1. 取出下一个待处理视频              │
│ 2. 打开视频页面（隐藏标签）          │
│ 3. content.js 提取媒体地址和Cookie   │
│ 4. 调用 POST /api/convert           │
│ 5. 轮询 GET /api/jobs/:jobId         │
│ 6. 转换完成后调用 chrome.downloads   │
│ 7. 更新视频状态为 completed          │
│ 8. 保存进度到 batch-store.json       │
│ 9. 等待15秒                         │
│ 10. 继续下一个视频                  │
└──────────────────────────────────────┘
    ↓
所有视频处理完成
    ↓
任务状态更新为 completed
    ↓
通知用户任务完成
```

### 3. 失败重试流程

```
视频下载/转换失败
    ↓
检查重试次数 < retryLimit (3次)
    ↓
是：retries++，等待30秒后重试
    ↓
否：标记为 failed，记录错误信息
    ↓
继续下一个视频
```

### 4. 断点续传流程

```
用户打开 batch.html
    ↓
从 batch-store.json 加载任务列表
    ↓
检查是否有 status = "running" 或 "paused" 的任务
    ↓
是：显示"继续任务"按钮
    ↓
用户点击"继续"
    ↓
从 currentIndex 位置恢复下载
```

### 5. 智能去重流程

```
开始处理下一个视频
    ↓
检查 downloadHistory 中是否存在该 BV号
    ↓
是：标记为 skipped，跳过
    ↓
否：正常下载
```

## API 设计

### 扩展内部消息 (Chrome Extension Messages)

#### 1. 解析合集信息

**请求** (batch.js → content.js):
```javascript
{
  type: "PARSE_COLLECTION",
  videoUrl: "https://www.bilibili.com/video/BV1xx411c7mD"
}
```

**响应** (content.js → batch.js):
```javascript
{
  ok: true,
  collection: {
    title: "【未来有悔】系列",
    videos: [
      { bvid: "BV1xx", title: "第1集", episode: 1, url: "https://..." },
      { bvid: "BV2yy", title: "第2集", episode: 2, url: "https://..." }
    ]
  }
}
```

#### 2. 启动批量任务

**请求** (batch.js → background.js):
```javascript
{
  type: "START_BATCH",
  batchJob: { /* BatchJob对象 */ }
}
```

**响应**:
```javascript
{
  ok: true,
  batchId: "uuid"
}
```

#### 3. 控制批量任务

**请求** (batch.js → background.js):
```javascript
{
  type: "PAUSE_BATCH" | "RESUME_BATCH" | "CANCEL_BATCH",
  batchId: "uuid"
}
```

## 实现策略

### Phase 1: 核心功能（MVP）

**优先级 P0 - 必须实现**:

1. **合集解析** (content.js)
   - 从页面DOM提取合集视频列表

   - 超时后跳过并继续

3. **暂停/恢复控制**
   - 暂停当前批量任务

   - 取消任务

4. **详细状态展示**

## 技术决策

### 决策1: 合集解析方案

**选择**: 方案A - DOM解析

**原因**:
- Bilibili API 可能需要额外的鉴权，且接口不稳定
- DOM解析可以直接使用浏览器的登录态
- 页面中已经渲染了完整的合集列表，直接提取即可
- 如果页面结构变化，只需更新选择器，不依赖外部API

**风险**: 页面结构变化可能导致解析失败，需要定期维护选择器

### 决策2: 批量任务存储方案

**选择**: 本地文件存储 (batch-store.json)

**原因**:
- 项目定位是纯本地工具，不依赖数据库
- JSON文件足够简单，易于调试和备份
- 数据量小（每个任务<100KB），性能足够

**替代方案**: Chrome Storage API - 但有5MB配额限制，且不便于服务端读取

### 决策3: 下载协调方式

**选择**: background.js 作为中心调度器

**原因**:
- background.js 是持久化的Service Worker，即使关闭页面也能继续运行
- 可以统一管理所有批量任务，避免冲突
- 与现有架构一致（background.js 已经负责调用本地API）

### 决策4: 复用 vs 重写转换逻辑

**选择**: 完全复用现有 `/api/convert` API

**原因**:
- 现有转换逻辑已经稳定可靠
- 批量下载只是编排层，不需要改动核心转换代码
- 降低风险，确保单个下载功能不受影响

## 风险和缓解措施

### 风险1: 页面结构变化导致解析失败

**影响**: 高  
**概率**: 中  
**缓解**:
- 使用多个备选选择器
- 添加详细的错误提示
- 提供手动输入BV号列表的备用方案

### 风险2: 下载过程中被B站限流

**影响**: 中  
**概率**: 低  
**缓解**:
- 设置15秒间隔降低请求频率
- 复用浏览器Cookie和User-Agent
- 失败后自动重试

### 风险3: 长时间运行导致浏览器关闭或崩溃

**影响**: 中  
**概率**: 中  
**缓解**:
- 每完成一个视频立即保存进度
- 支持断点续传
- 在batch.html显示明确的"保持页面打开"提示

### 风险4: 临时文件占满磁盘空间

**影响**: 低  
**概率**: 低  
**缓解**:
- 每个视频转换完成后立即清理临时文件
- 添加磁盘空间检查（未来优化）

## 总结

本设计文档完整描述了批量下载功能的需求、架构、实现策略和测试计划。核心设计原则是：

1. **渐进增强**: 不影响现有单个下载功能
2. **复用优先**: 最大程度复用现有转换逻辑
3. **容错设计**: 单个失败不影响整体
4. **状态持久**: 随时可中断和恢复
5. **用户友好**: 清晰的进度展示和错误提示

实现将分为3个阶段，优先完成MVP核心功能，后续根据用户反馈逐步增强。
